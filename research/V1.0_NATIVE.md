# V1.0 — Native (C++) build: design note

Status: design only. No native code has been written. The `cpp/` directory
holds a one-page README and nothing else.

This note exists so the v1.0 PR has a target to code against rather than
inventing a contract under deadline. It does three things:

1. Audits the current `cpp/` skeleton (one-line summary: it's a `README.md`).
2. Maps the existing Python surface that v1.0 must mirror or expose.
3. Identifies the cross-binary contract tests v1.0 needs to land green.

## What v1.0 actually means

From `research/ROADMAP.md`:

- `cpp/` minimal native CLI built on llama.cpp
- Shared tool protocol with the Python build
- Single static binary release on macOS + Linux
- Stable eval baseline; public release notes

The motivation in `cpp/README.md` reduces to two real wins: no Python
runtime in the distributed binary (`chmod +x thandv && ./thandv`), and
direct in-process llama.cpp (cuts the Ollama HTTP hop). Both are about
distribution and per-token latency, not about rewriting the assistant.

Concretely v1.0 ships:
- `cpp/external/llama.cpp` as a pinned submodule.
- `cpp/src/main.cpp` and friends — a single-binary CLI that links
  llama.cpp statically.
- A CMake build that produces `dist/thandv-native-{macos,linux}` (name
  separate from the existing Python `dist/thandv` until the C++ build
  is ready to be the default).
- A `release.yml` workflow update that attaches the native binary as a
  release artefact next to the PyInstaller one.
- A `tests/test_native_contract.py` that runs the C++ binary against
  fixture inputs and asserts the same observable behaviour as the
  Python `Agent` / `tools.dispatch` paths.

## Boundary: Python keeps the brain, C++ moves the bytes

The agent loop is cheap; the model is what costs. The right boundary
keeps the design surface (personas, skills, tools, sessions, memory,
config) on the Python side where it's already iterated on, and pushes
only the hot path to native:

| Surface                     | v1.0 home          | Rationale                                          |
|-----------------------------|--------------------|----------------------------------------------------|
| llama.cpp model I/O         | **C++**            | The point of the rewrite.                          |
| Streaming token loop        | **C++**            | Same hot path.                                     |
| Prompt assembly (system + skills + memory) | **C++ reads files written by Python helpers** | See "Directory contract" below. |
| Tool *dispatch* (read, write, edit, bash, retrieve) | **Python via subprocess** | Don't reimplement; shell out. |
| Tool *protocol* (call envelope, result envelope) | **shared** | See "Tool protocol" below.       |
| Personas / skills / evals   | **Python**         | Iteration speed wins; native binary reads outputs. |
| Sessions JSONL              | **C++**            | Native binary writes its own sessions to the same dir; format unchanged. |
| Config (THANDV_HOME, model, persona) | **shared file**  | Both binaries read `~/.thandv/config.json`.        |
| `~/.thandv/corpora/`        | **Python writes, C++ reads (via `thandv` shell-out)** | RAG embed model is Ollama-side; native binary calls Python helper for retrieve. |
| `~/.thandv/training/`       | **Python only**    | Trainer stays Python — MLX-LM + llama.cpp convert. |

The principle: anything the v0.x lineage iterated on stays Python. The
native binary is a *front-end* for inference, not a rewrite of the
assistant.

## Tool protocol (JSON over stdin / stdout)

The C++ binary needs to invoke six tools today (`tools.TOOLS`):
`read_file`, `write_file`, `edit_file`, `list_dir`, `run_bash`,
`retrieve`. Plus whatever lands between this note and v1.0.

The contract reuses the existing Python tool registry rather than
reimplementing it. A new `thandv` subcommand will be added in the v1.0
PR (not in this note):

```
$ thandv tool dispatch read_file <<EOF
{"path": "/tmp/x.txt"}
EOF
{"path": "/tmp/x.txt", "content": "..."}
```

Exit code 0 means the tool ran (the result dict's `error` key signals a
tool-level error, distinct from a dispatch failure). Exit code 2 means
the dispatcher couldn't parse the request. The C++ binary spawns
`thandv tool dispatch <name>`, writes the JSON args to stdin, reads the
JSON result from stdout. This is the same shape `tools.dispatch(name,
args)` already returns — no new envelope to invent.

The tool list and schemas are exposed by a separate subcommand so the
C++ binary can self-discover what's available:

```
$ thandv tool schemas
{"version": "1", "tools": [{"name": "read_file", ...}, ...]}
```

`version` lets v1.0+ binaries refuse to talk to a Python toolside that
breaks the contract. Bump on any breaking change to TOOL_SCHEMAS shape.

The native model loop emits tool calls via the *same* three protocols
the Python agent already supports (see `agent.py:_extract_tool_call`,
`_extract_inline_json_tool_call`, `_normalise_native_call`). llama.cpp
doesn't have OpenAI-style native `tool_calls` output, so the C++ binary
will rely on the text-fenced ```tool``` protocol first and fall back to
inline JSON — same priority order as the Python side, just without the
native-call branch.

## Directory contract (shared between binaries)

Both binaries read and write under `~/.thandv/` (overridable with
`$THANDV_HOME`). The layout in `docs/USAGE.md` stays authoritative:

```
~/.thandv/
├── config.json
├── sessions/<unix-ts>.jsonl       # both binaries append here
├── skills/<stem>.md                # user overrides
├── memory/<topic>.md
├── evals/                          # Python only (eval harness stays Python)
├── corpora/<persona>/chunks.jsonl  # Python writes, both read via `thandv tool dispatch retrieve`
└── training/                       # Python only
```

Bundled skills (`thandv/skills/*.md`, shipped via `pyproject` package-data
since v0.10) need to be reachable from the native binary too. Two options:

1. **Native binary embeds them at link time** via `xxd -i` or a CMake
   `configure_file` step that bakes the bytes in. Pro: truly single
   binary, no install-side file dependence. Con: rebuilding to add a
   skill.
2. **Native binary discovers them next to itself** at a known relative
   path (`./share/thandv/skills/`). Pro: skills updatable without
   rebuilding. Con: not strictly a "single static binary" any more.

Recommendation for v1.0: option 1 (embed at link time). The skills are
small (the current six total ~5 KB), they're versioned with the binary
the way the rest of the persona / prompt layer is, and "single static
binary" is the v1.0 distribution promise.

## Build infrastructure

- **Submodule**: `git submodule add https://github.com/ggerganov/llama.cpp
  cpp/external/llama.cpp` — pin to a known-good commit, document it in
  `cpp/README.md`. Bumping is a deliberate PR, not a sweep.
- **CMake**: `cpp/CMakeLists.txt` builds `thandv-native` linking
  llama.cpp statically. Disable llama.cpp's server / examples
  (`-DLLAMA_BUILD_TESTS=OFF -DLLAMA_BUILD_EXAMPLES=OFF
  -DLLAMA_BUILD_SERVER=OFF`) to keep the binary lean.
- **macOS**: Metal backend enabled by default; arm64 build via CMake's
  `-DCMAKE_OSX_ARCHITECTURES=arm64`. Universal binary out of scope for
  v1.0 (arm64 covers the relevant Apple Silicon hardware; x86_64 macs
  can use the Python build).
- **Linux**: CPU build first (CUDA / ROCm gated behind separate
  build-time flags for v1.1). Static link against musl is *not*
  promised — glibc against Ubuntu 22.04 baseline matches what we
  already do in `release.yml`.
- **CI**: a new `native-build` job in `.github/workflows/ci.yml` that
  runs `cmake -B cpp/build -S cpp && cmake --build cpp/build` on
  ubuntu-22.04 and macos-14. Smoke-runs `./cpp/build/thandv-native
  --version`. Full inference is too heavy for PR CI; that's manual or
  nightly.

## Cross-binary contract tests

Existing Python tests that already encode the contract the native
binary must honour:

| Existing test                                     | What it pins                                        |
|---------------------------------------------------|-----------------------------------------------------|
| `tests/test_tools.py`                             | Tool argument shapes, error envelope, dispatch behaviour. The native binary calls these via subprocess; the tests still apply because the *Python side* is being shelled out to. |
| `tests/test_tools.py::test_run_bash_refuses_destructive_without_confirm` | Safety contract (`rm -rf` etc. need `confirm=True`). Native binary should not bypass. |
| `tests/test_memory.py::test_user_skill_overrides_bundled` | Skill loading precedence. Native binary embedding bundled skills must still honour user overrides from `~/.thandv/skills/`. |
| `tests/test_memory.py::test_real_bundled_skills_dir_ships_strategy_critique` | The bundled set is part of the wheel contract; native binary embeds the *same* set. |
| `tests/test_agent.py` (the existing agent tests)  | Tool-block parsing, fallback ordering, hop budget, duplicate-call guard. Native binary's agent loop has to behave the same way for the same inputs. |
| `tests/test_personas.py`                          | The persona registry shape. Native binary reads `thandv personas list` (subcommand to add) to know what personas exist. |

New tests v1.0 needs to land green:

- `tests/test_tool_dispatch_cli.py` — exercises `thandv tool dispatch
  <name>` over real stdin/stdout subprocess, asserts JSON in / JSON
  out, exit codes for happy path / unknown tool / malformed JSON /
  tool-error envelope. (Can be written BEFORE the native binary
  exists; it pins the Python side of the protocol.)
- `tests/test_tool_schemas_cli.py` — exercises `thandv tool schemas`,
  asserts version field, every TOOL has a schema, every schema has a
  TOOL.
- `tests/test_native_contract.py` (skipped by default with
  `pytest.skip("native build not present")` unless
  `cpp/build/thandv-native` exists): runs the native binary against
  fixture prompts that *don't* require a live model — e.g. `--version`,
  `--help`, schema self-check, tool-dispatch round-trip — and asserts
  the same observable behaviour as the Python equivalents.
- Optional: a tiny llama.cpp smoke test gated behind an env var
  (`THANDV_NATIVE_MODEL=/path/to/q4_0.gguf`) that runs one inference
  and checks for non-empty output. Off by default; on for the nightly.

## Phased plan

Doing this in one PR will be painful. Suggested split:

1. **PR A (small, Python-only)**: ship `thandv tool dispatch <name>`
   and `thandv tool schemas`. No native code. Adds
   `test_tool_dispatch_cli.py` and `test_tool_schemas_cli.py`. Bumps
   the contract version field to `"1"`. Locks in the protocol.

2. **PR B (medium, native skeleton)**: `cpp/external/llama.cpp`
   submodule + `cpp/CMakeLists.txt` + `cpp/src/main.cpp` that loads a
   GGUF and runs one prompt non-interactively (`thandv-native --model
   path.gguf --prompt "hi"`). No tool support yet. CI native-build
   job lands. `tests/test_native_contract.py` exercises `--version`
   and `--help` only.

3. **PR C (medium, tool loop in C++)**: implement the ```tool``` block
   parser + subprocess dispatch to `thandv tool dispatch`. Wire the
   text-fenced and inline-JSON fallbacks. Add `--persona`, skill
   embedding via CMake `configure_file`. `test_native_contract.py`
   exercises a real tool round-trip (read_file against a fixture).

4. **PR D (small, release pipeline)**: extend `.github/workflows/release.yml`
   to attach `thandv-native-{macos-14,ubuntu-22.04}` artefacts when a
   `v1.0.0` tag is pushed. Tag and ship.

Total: ~3-4 PRs over a few sessions, each independently mergeable, each
with green CI before the next starts.

## Open questions

- **GGUF download UX in the native binary.** Today `install.sh` calls
  `ollama pull`. The native binary can't shell out to Ollama (whole
  point of removing it). Options: ship a separate `thandv-native pull
  <model>` that wraps HF Hub; or document that users `huggingface-cli
  download` themselves. Recommendation: defer to v1.1; v1.0 expects
  `--model /path/to/x.gguf` as a required arg.
- **Adapter loading.** The training track produces LoRA adapters that
  llama.cpp can load. The Python side picks the adapter per persona
  (`trainer.state.active_models_by_persona`). The native binary needs
  to read that state file and pass `--lora` to llama.cpp. State file
  shape is already JSON; just read it.
- **Sessions JSONL writing from C++.** Format is a sequence of
  `{role, content}` plus `{role: "tool", name, result}` lines. Trivial
  to emit; the only catch is the timestamp-based filename collision if
  the Python and native binaries start the same nanosecond. Mitigation:
  PID suffix.
- **Windows.** Out of scope for v1.0, per cpp/README.md. macOS arm64
  and Ubuntu 22.04 x86_64 only.

## What this note is not

A green light. v1.0 is a real chunk of native work — submodule pinning,
CMake on two platforms, llama.cpp ABI churn, the protocol round-trip
testing. The phased plan above is the honest minimum to land it without
a doomed mega-PR. If anything in this note proves wrong on first
contact with the C++ code, change the note before changing the code.
