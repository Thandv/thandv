# v0.4 — real LoRA training pipeline (design memo)

This memo names the open decisions that have to be made before we plug
actual weight updates into the trainer daemon (the scaffold landed in v0.2,
[`thandv/trainer.py`](../thandv/trainer.py)). Each section ends with a
**recommendation**, but the call is yours.

## 1. What's already built (don't redesign)

- **`trainer.tick()`** does: pull queue → train (stub) → eval-gate → promote
  or discard. The stub writes a marker file; everything else around it is
  real.
- **Queue** at `~/.thandv/training/queue/` (JSONL of `{prompt, completion}`).
- **Eval-gate** runs the smoke suite; with this memo's PR-trail it can also
  run `humaneval` / `mbpp` / `writer` / `finance` once we wire suite
  selection through trainer config.
- **Daemon control** (`thandv train run/tick/status/pause/resume/stop`) and
  **launchd / systemd templates** are shipped and tested.
- **No new architecture work** is needed above `_stub_train(queue_file)
  -> adapter_id`. The new code goes *inside* that function (plus
  conversion + loading on either side).

## 2. The four decisions

### 2.1 Trainer backend

| Option | Hardware | Status | Notes |
|---|---|---|---|
| **Unsloth** | CUDA only (Linux/Win) | Mature, fastest 7B LoRA in industry | No M-series support; pinned to NVIDIA |
| **MLX-LM** | Apple Silicon only | Apple-blessed, M-series-native | Smaller ecosystem; LoRA training works |
| **HF Transformers + PEFT** | Universal | Slow on M-series but works | The reference impl most papers target |
| **tinygrad** | Universal | Young, evolving | Risky for v0.4; revisit at v0.6+ |

**Recommendation.** A tiny **backend abstraction** in `thandv/trainer.py`
that picks the strongest backend the host can run. Today's machine is
M-series, so MLX-LM is the immediate target; CUDA boxes pick Unsloth; CPU /
fallback picks HF+PEFT. The trainer doesn't care which fired — `_stub_train`
becomes `_train(queue_file, backend)`.

The abstraction is two functions:

```python
class TrainerBackend(Protocol):
    def train(self, base_model: Path, queue_file: Path, out_dir: Path) -> Path: ...
    def is_available(self) -> bool: ...

BACKENDS = [UnslothBackend(), MLXBackend(), HFPEFTBackend()]
def pick_backend() -> TrainerBackend:
    return next(b for b in BACKENDS if b.is_available())
```

This is ~40 lines + one impl. The first impl is what gates v0.4.

### 2.2 Base-model format pipeline

Ollama serves models as **GGUF**. Trainers want **safetensors / HF format**.
We need a one-time conversion and a re-conversion after training.

Two paths:

1. **Pull from HF, train on HF, convert to GGUF for Ollama.**
   - Pro: cleanest, what every trainer expects.
   - Con: we now manage two copies of every base model (~14 GB for 7B on
     M2 16 GB if we keep both around).

2. **Convert Ollama's GGUF → HF for training, then GGUF back for serving.**
   - Pro: one source of truth (the Ollama install).
   - Con: GGUF→HF conversion is lossy on some quantisations; round-tripping
     a Q4 GGUF for training is a bad idea.

**Recommendation.** Path 1. Pull the base model in HF format on first
`thandv train enable`, train on that, convert to GGUF for serving. Disk
cost is real but predictable. Stash HF under
`~/.thandv/training/base/<model>/` so it's clearly opt-in.

GGUF conversion: `llama.cpp/convert_hf_to_gguf.py` is the standard tool —
vendor the script, or invoke a pinned `llama.cpp` release as a subprocess.

### 2.3 Serving the trained adapter

Three options for how Ollama sees the LoRA after training:

1. **Merge adapter into base, write a new GGUF, create Ollama Modelfile
   `FROM <new>.gguf`.**
   - Pro: identical inference codepath; no Ollama features required.
   - Con: a full-size GGUF per promoted adapter (~4–8 GB each). Storage
     grows fast.

2. **Ollama Modelfile `FROM <base>` + `ADAPTER <adapter.gguf>`.**
   - Pro: tiny per-adapter file (~30–100 MB), composable.
   - Con: depends on Ollama's adapter support being stable and on
     llama.cpp's LoRA inference path working for the chosen quantisation.

3. **Side-channel: serve trained adapter via direct llama.cpp + a new
   `thandv` HTTP shim, only for adapter-active sessions.**
   - Pro: no Ollama coupling.
   - Con: meaningfully more code; second runtime path.

**Recommendation.** Start with **(1)** — merged GGUF per promoted adapter.
Simpler, fully tested codepath, no Ollama feature dependency. Add
adapter-stacking (2) later once we have multiple promoted adapters and
disk pressure is real. Keep `_stub_train` returning an adapter id that's a
*filename pointing at a merged GGUF*, not a LoRA-only artefact.

Storage policy: keep at most N promoted adapters; rotate out the worst by
eval pass rate.

### 2.4 Hardware budget on this machine

The current dev machine is **M2 16 GB**. Honest reality:

- Inference: `qwen2.5-coder:7b` at Q4_K_M runs comfortably.
- Training: 7B QLoRA on 16 GB unified memory is **tight**. MLX-LM can do
  it with very small batch sizes and short context windows. Practical
  rates are likely a few hundred tokens/sec, training runs in tens of
  minutes to a few hours per adapter.
- 3B LoRA fits comfortably with room to spare. Strong fit for a research
  pipeline that iterates.

**Recommendation.** Default the trainer base to `qwen2.5-coder:3b` for
M-series 16 GB hosts, with an opt-in to 7B that warns about memory.
NVIDIA hosts default to 7B. Decision lives in `runtime.pick_model` —
already host-aware.

## 3. Phased plan

| Phase | Scope | Approx LOC |
|---|---|---:|
| **v0.4.0** | Backend abstraction interface; HF base-model fetch; HF→GGUF round-trip; **one backend wired** (MLX-LM on this machine). `_stub_train` becomes `_train_lora(queue_file)`. | ~600 |
| **v0.4.1** | Unsloth backend (CUDA hosts). | ~250 |
| **v0.4.2** | Adapter-merge → Modelfile → Ollama load path. End-to-end: tick → train → merge → reload Ollama → eval → promote. | ~200 |
| **v0.4.3** | HF+PEFT fallback for non-MLX non-CUDA hosts. | ~150 |
| **v0.4.4** | Storage policy: keep N best adapters, rotate. | ~80 |

Each phase ships its own PR, eval-gated, no flag day.

## 4. Risks, open questions, decisions for you

- **Storage growth.** Merged-adapter strategy means each promoted run costs
  ~4–8 GB. On a research laptop this adds up. Acceptable, or should v0.4.0
  ship with the storage rotator already in (move to v0.4.0 from v0.4.4)?
- **3B default.** Are you OK with the trainer running 3B by default on
  16 GB hosts even though chat uses 7B? Different models for inference
  vs training is fine in principle but worth confirming.
- **MLX-LM stability.** It's actively developed; pinning a version is
  important. Pin once at v0.4.0, bump deliberately.
- **GGUF conversion script.** Vendor it (one file, predictable) or invoke
  upstream `llama.cpp` (latest features, fragile)?
- **Eval suite to gate on.** Currently the trainer's `tick` uses `smoke`.
  v0.4 should let trainer config pick. Default to `humaneval` for the code
  persona's adapters? Or stay on `smoke` for fast iteration and gate
  promotion-to-active on the bigger suite?
- **Where do we draw the line on "successful training" in v0.4.0?** I'd
  call success: train a tiny LoRA on a 10-example queue file, the eval
  pass rate doesn't regress, the adapter loads into Ollama, the model
  produces output. *Quality improvement* over baseline is a separate goal
  — the verifier-filtered synthetic data pipeline (v0.6) is what actually
  moves numbers.
